1บทสรุป

KinWhy AI รับภาพถ่ายมื้ออาหารหนึ่งภาพ แล้วตอบว่าในจานมีพื้นที่ของ ผัก (หมู่ 3) ข้าว-แป้ง (หมู่ 2) โปรตีน (หมู่ 1) และ ผลไม้ (หมู่ 4) อย่างละเท่าไร และจานนั้นใกล้สูตร จานสุขภาพ 2:1:1 ของกรมอนามัย (ผักครึ่งจาน ข้าว-แป้งหนึ่งในสี่ โปรตีนหนึ่งในสี่) แค่ไหน

หัวใจของระบบคือโมเดล semantic segmentation ซึ่งระบุว่าแต่ละพิกเซลในภาพเป็นอาหารประเภทใด โดยใช้สถาปัตยกรรม SegFormer-B2 ที่นำน้ำหนักเริ่มต้นจากชุดข้อมูล ADE20K มาเทรนต่อ (fine-tune) กับข้อมูลอาหาร 16,450 ภาพ โมเดลให้ผลออกมาสองส่วนในการรันครั้งเดียว:

  1. แผนที่คลาสรายพิกเซล 11 คลาส ความละเอียด 128×128 เมื่อนับพื้นที่แต่ละคลาสแล้วแปลงเป็นหมู่อาหาร ก็จะได้สัดส่วนบนจาน
  2. ความน่าจะเป็นว่าภาพนี้เป็นอาหารหรือไม่ (food gate) ใช้กันภาพที่ไม่ใช่อาหาร

จุดที่ต่างจากงานทั่วไปคือ ชุดข้อมูลอาหารไทย 494 ภาพที่ติดป้ายระดับพิกเซล ซึ่งสร้างขึ้นเองด้วยกระบวนการกึ่งอัตโนมัติ ให้ SAM 2.1 วาดขอบวัตถุ แล้วตรวจและแก้ป้ายของทุกส่วนทีละภาพ ชุดนี้แบ่งเป็นชุดทดสอบ 149 ภาพ ซึ่งเป็นครั้งแรกที่วัดความแม่นยำบนอาหารไทยได้จริง และชุดเทรน 345 ภาพ ซึ่งทำให้โมเดล v4 แม่นขึ้นชัดเจนบนอาหารไทย

2ภาพรวมระบบและการไหลของข้อมูล

ระบบแบ่งเป็นสามชั้นที่แยกจากกันชัดเจน:

  • ชั้นการรับรู้ (perception): โมเดลแบ่งพื้นที่ (หัวข้อ 5-9) ตอบได้อย่างเดียวว่า "พิกเซลนี้คืออะไร"
  • ชั้นกฎโภชนาการ (rules): ฟังก์ชันที่กำหนดแน่นอน (deterministic) ใน backend/nutrition.py แปลงพื้นที่เป็นสัดส่วนหมู่อาหาร คะแนน 2:1:1 และคำแนะนำ (หัวข้อ 3, 10) ชั้นนี้ไม่มี machine learning ผลจึงตรวจสอบย้อนกลับได้ทุกตัวเลข
  • ชั้นแสดงผล: เว็บ แอป และประวัติ (หัวข้อ 13)

การแยกแบบนี้ทำให้ตัวเลขที่ผู้ใช้เห็นตรงกับสีที่ระบายบนภาพเสมอ เพราะสัดส่วนคำนวณจากหน้ากากสีเดียวกัน ไม่มีโมเดลอีกตัวมาทำนายสัดส่วนแยกต่างหาก ซึ่งต่างจากรุ่นก่อนหน้าที่เคยมีหัวทำนายสัดส่วนแยก และให้ตัวเลขไม่ตรงกับภาพ

5สถาปัตยกรรมโมเดล

5.1 ทำไมเลือก SegFormer

SegFormer (Xie et al., NeurIPS 2021) เป็นโมเดล segmentation แบบ Transformer ที่ออกแบบให้เบา มีจุดเด่นที่เหมาะกับงานนี้:

  • ไม่มี positional encoding แบบตายตัว จึงรับภาพต่างขนาดได้โดยความแม่นไม่ตก เหมาะกับรูปจากมือถือที่สัดส่วนภาพไม่เท่ากัน
  • Encoder แบบลำดับชั้น (hierarchical) ให้ feature 4 ระดับความละเอียด จับได้ทั้งเม็ดข้าวและภาพรวมของจาน
  • Decoder เป็น MLP ล้วน เบาและแปลงเป็น ONNX หรือ quantize ได้ง่าย ทำให้รันในเบราว์เซอร์ได้
  • รุ่น B2 สมดุลระหว่างความแม่นกับขนาดไฟล์ (int8 ประมาณ 55 MB)

5.3 ส่วนที่เราดัดแปลง

  1. หัวแบ่งคลาส เปลี่ยนจาก 150 คลาสของ ADE20K เป็น 11 คลาส โดยสุ่มค่าเริ่มต้นใหม่เฉพาะชั้นสุดท้าย ส่วนอื่นใช้น้ำหนัก ADE20K เดิม
  2. หัว food gate นำ feature ของ stage สุดท้าย (512 ช่อง ที่ 1/32) มาทำ global average pooling และ global max pooling แล้วต่อกันเป็น 1,024 ค่า → Linear(1024→256) → LayerNorm → SiLU → Dropout 0.2 → Linear(256→1) ผ่าน sigmoid ได้ความน่าจะเป็นที่ภาพจะเป็นอาหาร
ขาเข้า : pixel_values (1, 3, 512, 512) float32, normalize ด้วย mean/std ของ ImageNet ขาออก : seg_logits (1, 11, 128, 128) ค่าก่อน softmax ต่อคลาส ต่อพิกเซล (stride 4) food_logit (1, 1) ค่าก่อน sigmoid ของ "ภาพนี้เป็นอาหาร"

6.3 การสร้าง pseudo-label สำหรับภาพที่ไม่มีป้าย (training/relabel_thai.py)

ภาพ THFOOD-50 มีแค่ชื่อเมนู จึงให้โมเดลรุ่นก่อน (teacher, v3) ติดป้ายให้ก่อน แล้วกรองให้สะอาดขึ้นสามชั้น:

  1. Test-time augmentation แบบกลับซ้ายขวา: รันทั้งภาพปกติและภาพที่กลับซ้ายขวา แล้วเฉลี่ย logits ลดความผิดพลาดแบบสุ่ม
  2. Dish prior: แต่ละเมนูกำหนดคลาสที่เป็นไปได้ไว้ เช่น กะเพราจะมีได้แค่ โปรตีน ข้าว ไข่ ผัก ความน่าจะเป็นของคลาสที่ไม่ควรมีจะถูกตั้งเป็น 0 ก่อนเลือกคลาส ป้องกันความผิดแปลกๆ เช่น ผลไม้ในกะเพรา
  3. Ignore label: พิกเซลที่ความมั่นใจสูงสุดต่ำกว่า 0.60 ให้ค่า 255 (ไม่นำมาคิด loss) โดยเฉลี่ยตัดออก 8.0% ของพิกเซล หลักคือพิกเซลที่ไม่แน่ใจไม่ควรสอนอะไร ดีกว่าสอนสิ่งที่เดาไว้
ข้อจำกัดของ pseudo-label: ป้ายมาจากโมเดล teacher จึงมีอคติเดียวกับ teacher เช่น v3 มักอ่านหมูสับเป็นข้าว นักเรียนก็จะเรียนความผิดนั้นต่อไปด้วย ผลการทดลอง v3b ยืนยันเรื่องนี้ คือเพิ่มภาพไทยเป็นสองเท่าแต่แทบไม่ดีขึ้นบน FoodSeg103 นี่คือเหตุผลที่ต้องสร้างชุดข้อมูลที่ตรวจด้วยมือในหัวข้อ 7

7การสร้างป้ายกำกับอาหารไทย (SAM + การตรวจทีละส่วน)

ไม่มีชุดข้อมูลอาหารไทยสาธารณะที่ติดป้ายระดับพิกเซล การวาดขอบด้วยมือทั้งหมดใช้เวลาประมาณ 10-20 นาทีต่อภาพ จึงออกแบบกระบวนการให้ โมเดลวาดขอบ และคนตัดสินว่าแต่ละส่วนคืออะไร ใช้เวลาเฉลี่ยราว 1-2 นาทีต่อภาพ

7.1 การเลือกภาพ (training/select_thai.py)

  • ชุดทดสอบใช้ 3 ภาพต่อเมนู × 50 เมนู = 150 ภาพ ชุดเทรนใช้ 4 ภาพต่อเมนู บวกอีก 10 ภาพสำหรับ 15 เมนูที่ยาก (ข้าวราดหน้า อาหารคลุก โจ๊ก) รวม 346 ภาพ
  • ป้องกันข้อมูลรั่ว: ภาพ THFOOD ทุกภาพที่เคยใช้เทรนในรุ่นใดก็ตาม (8,201 ภาพ) ถูกย่อเป็นภาพขาวดำ 16×16 แล้วเทียบระยะเฉลี่ยกับภาพที่จะเลือก ภาพที่ระยะต่ำกว่า 3.0 (ระดับสีจาก 0-255) ถือว่าเคยใช้แล้ว ไม่นำมาใช้เลย ทั้งในชุดทดสอบและชุดเทรนใหม่

7.2 ขั้นตอนต่อภาพ (training/sam_label.py)

  1. SAM 2.1 (hiera-large) โหมดอัตโนมัติ สร้างหน้ากากทั่วภาพ ตั้ง pred_iou_thresh=0.7, stability_score_thresh=0.85 แล้วนำหน้ากากมาเรียงจากใหญ่ไปเล็ก ส่วนที่เล็กกว่าทับส่วนที่ใหญ่กว่า ได้แผนที่ส่วน (region) ที่ไม่ซ้อนกัน ส่วนที่เล็กกว่า 0.2% ของภาพถูกรวมเข้า "ส่วนที่เหลือ"
  2. เติมช่องว่าง: SAM มักไม่ครอบคลุมกองอาหารใหญ่ๆ เช่น กองหมูสับ พิกเซลที่ไม่มีส่วนจะถูกแบ่งตามคลาสที่โมเดลเดาและตาม connected component เป็นส่วนใหม่ (ขั้นต่ำ 0.4% ของภาพ) เพื่อให้ถูกตรวจด้วย
  3. ข้อเสนอคลาส: โมเดล (v3 สำหรับชุดทดสอบ, v3b สำหรับชุดเทรน) เสนอคลาสของแต่ละส่วนด้วยการโหวตเสียงข้างมากของพิกเซลในส่วนนั้น
  4. แผ่นตรวจ (contact sheet): ภาพต้นฉบับคู่กับภาพที่ระบายสีตามข้อเสนอ แต่ละส่วนมีหมายเลขและรหัสคลาสวางไว้ที่จุดลึกสุดของส่วน (คำนวณจาก distance transform) ป้ายจึงไม่ตกขอบหรือทับส่วนอื่น
  5. การตรวจ: ผู้ตรวจดูภาพทุกภาพแล้วบันทึกการแก้ลง training/thai_labels.json ได้หลายรูปแบบ:
    • แก้คลาสรายส่วน เช่น "5": "P" (ส่วนที่ 5 คือโปรตีน)
    • map แก้คลาสทั้งภาพ เช่น {"R": "P"} (ทุกส่วนที่ถูกเสนอเป็นข้าวให้เป็นโปรตีน)
    • boxes ระบายในกรอบสี่เหลี่ยม ใช้เมื่อ SAM รวมสองอย่างเป็นส่วนเดียว โดยกำหนดให้ระบายเฉพาะพิกเซลที่เป็นคลาสหนึ่งได้
    • X = ไม่แน่ใจ (ignore) เช่น ซุปปนผัก ซอส เงา
    • v3 = ใช้ป้ายรายพิกเซลของโมเดลในส่วนที่ SAM ตัดคร่อมอาหารกับพื้นหลัง
    • skip = ไม่ใช้ภาพนี้
  6. ตรวจซ้ำ: เรนเดอร์ป้ายสุดท้ายเทียบกับภาพจริงอีกรอบ เพื่อจับความผิดพลาดจากการแก้

8การเทรนโมเดล

8.1 การเตรียมภาพ (ใช้แบบเดียวกันทุกที่)

  1. ย่อภาพโดยรักษาสัดส่วน ให้ด้านยาว = 512 พิกเซล ตอนเทรนสุ่มด้านยาวระหว่าง 384-512 (scale augmentation)
  2. แปลงค่าเป็น 0-1 แล้ว normalize ด้วย mean (0.485, 0.456, 0.406) และ std (0.229, 0.224, 0.225)
  3. เติมขอบขวาและล่างจนได้ 512×512 ด้วยการคัดลอกพิกเซลขอบ (edge padding) และตั้งป้ายของส่วนที่เติมเป็น 255 (ไม่คิด loss)
  4. ย่อป้ายเป็น 128×128 ด้วย nearest neighbour ให้ตรงกับขนาดขาออกของโมเดล

การเติมขอบแทนการบีบภาพเป็นสี่เหลี่ยมจัตุรัสช่วยให้อาหารไม่ผิดสัดส่วน ซึ่งสำคัญเพราะผลลัพธ์คือสัดส่วนพื้นที่

8.2 Data augmentation (เฉพาะตอนเทรน)

  • กลับซ้ายขวา โอกาส 50%
  • ปรับแสง (brightness 0.75-1.25), contrast (0.8-1.2) และความอิ่มของสี (0.8-1.2) โอกาส 70% เพื่อรองรับแสงร้านอาหารที่ต่างกัน
  • สุ่มขนาด 384-512 ก่อนเติมขอบ

8.3 ฟังก์ชัน loss

L = CE_weighted(seg) + 0.6 · Dice(seg) + 0.4 · BCE(food) CE_weighted : cross-entropy ถ่วงน้ำหนักรายคลาส, ignore_index = 255, label smoothing 0.03 น้ำหนัก [bg 0.5, rice 1.0, starch 1.1, animal 1.0, egg 1.4, plant 1.5, veg 1.0, fruit 1.4, mixed 1.2, sweets 1.3, liquid 1.2] Dice : soft Dice เฉลี่ยเฉพาะคลาสที่ปรากฏใน batch (ไม่นับพิกเซล 255) BCE : binary cross-entropy ของ food gate (อาหาร = 1, ไม่ใช่อาหาร = 0)

Cross-entropy ทำให้ทุกพิกเซลถูกต้อง ส่วน Dice ชดเชยคลาสพื้นที่เล็ก เช่น ไข่หรือผลไม้ ที่ cross-entropy มักมองข้าม และน้ำหนักพื้นหลังต่ำ (0.5) ช่วยไม่ให้โมเดลเลือกตอบพื้นหลังเพื่อความปลอดภัย

9การแปลงโมเดลและการรันจริง (inference)

9.1 Export

  • ONNX fp32: torch.onnx.export opset 17 ได้ไฟล์ 110.8 MB ใช้บนเซิร์ฟเวอร์ ความแม่นยำเต็ม
  • ONNX int8: dynamic quantization (onnxruntime) เฉพาะ MatMul/Gemm น้ำหนักเป็น QUInt8 ได้ไฟล์ 54.7 MB ใช้ในเบราว์เซอร์ ความแม่นลดลงเล็กน้อย (หัวข้อ 11.3)
  • ไฟล์คำอธิบาย model.json เก็บรายชื่อคลาส ขนาดขาเข้า stride และ mean/std ให้ทุกที่อ่านค่าชุดเดียวกัน

9.2 ขั้นตอนหลังโมเดล

  1. ตัดส่วนที่เติมขอบออก: ใช้เฉพาะพื้นที่ (ความสูงจริง/4) × (ความกว้างจริง/4) ของแผนที่ 128×128
  2. argmax เลือกคลาสที่ logit สูงสุดต่อพิกเซล
  3. ลบจุดเล็ก (speck removal): คลาสที่มีพื้นที่รวมน้อยกว่า 0.3% ของภาพให้เป็นพื้นหลัง กันเศษสีเล็กๆ ที่ทำให้สัดส่วนเพี้ยน
  4. Food gate: ถือว่าภาพเป็นอาหารเมื่อ sigmoid(food_logit) ≥ 0.5 และ พื้นที่อาหารรวม ≥ 2% ของภาพ ถ้าไม่ผ่าน ให้แจ้งว่า "ไม่พบจานอาหาร"
  5. นับพื้นที่ ของแต่ละคลาสเป็นสัดส่วนของภาพ แล้วส่งต่อให้ชั้นกฎโภชนาการ (หัวข้อ 10)
  6. ภาพซ้อนสี (overlay): แผนที่คลาสถูกระบายสีตามหมู่ ขยาย 4 เท่าแบบ bilinear ให้ขอบนุ่ม แล้ววางทับภาพจริงที่ความโปร่งใส 45%

10การคำนวณสัดส่วนจานและคะแนน 2:1:1

ฟังก์ชัน plate_area() ใน backend/nutrition.py รับพื้นที่ของแต่ละคลาส (สัดส่วนของภาพ 0-1) แล้วคำนวณดังนี้

1) พื้นที่หมู่ g = Σ_คลาส c พื้นที่(c) × สัดส่วนแบ่ง(c → g) - background ไม่นับ · liquid แยกเป็น liquid_coverage ไม่นับในจาน - mixed_dish แบ่ง 65/25/10 (หรือตาม VLM ถ้ามี) 2) อัตราส่วน 2:1:1 (ไม่รวมผลไม้) main = พื้นที่ผัก + พื้นที่แป้ง + พื้นที่โปรตีน veg% = 100 × ผัก / main (เป้า 50) carb% = 100 × แป้ง / main (เป้า 25) prot% = 100 × โปรตีน / main (เป้า 25) 3) คะแนน = max(0, 100 × (1 − D / 150)) โดย D = |veg%−50| + |carb%−25| + |prot%−25| 150 คือ D มากที่สุดที่เป็นไปได้ (เช่น 0:100:0) คะแนนจึงอยู่ในช่วง 0-100 แบบเส้นตรง ถ้า main = 0 (มีแต่ผลไม้หรือเครื่องดื่ม) จะไม่ให้คะแนน

ตัวอย่าง: ข้าวมันไก่ที่วัดได้ ผัก 7% แป้ง 51% โปรตีน 42% จะได้ D = 43 + 26 + 17 = 86 คะแนน = 100 × (1 − 86/150) = 43 (แอปปัดเป็นจำนวนเต็ม)

11.1 ตัวชี้วัด (training/evaluate.py)

วัดจากไฟล์ ONNX ที่ใช้งานจริง ไม่ใช่จาก checkpoint ตอนเทรน ตัวเลขจึงรวมผลของการ export, quantization และขั้นตอนหลังโมเดลทั้งหมด

  • IoU (Intersection over Union) ของคลาสหรือกลุ่ม = พิกเซลที่ทายถูก ÷ (พิกเซลที่ทายว่าเป็น ∪ พิกเซลที่เป็นจริง) และ mIoU = ค่าเฉลี่ยของ IoU
  • mIoU 5 กลุ่ม: พื้นหลัง โปรตีน แป้ง ผัก ผลไม้ ในพิกเซลที่ป้ายจริงเป็นอาหารคลุก ขนม หรือของเหลว จะไม่นับ เพื่อเทียบโมเดลที่มีคลาสต่างกันได้อย่างยุติธรรม ถ้าโมเดลทายเป็นคลาสเหล่านั้นบนพิกเซลที่เป็นอาหารชัดเจน จะนับเป็นการทายผิด
  • ค่าคลาดเคลื่อน 2:1:1 (ตัวเลขที่ผู้ใช้เห็นจริง) = ค่าเฉลี่ยของ |veg%−veg%จริง|, |carb%−carb%จริง|, |prot%−prot%จริง| ต่อจาน แล้วเฉลี่ยทุกจาน หน่วยเป็นจุดเปอร์เซ็นต์ ถ้าโมเดลไม่พบอาหารบนจานที่มีอาหารจริง ให้นับเป็นความผิดสูงสุด (66.7) บนชุดไทย พิกเซลที่ตั้งเป็น "ไม่แน่ใจ" จะไม่ถูกนำมาคิดทั้งฝั่งจริงและฝั่งที่ทาย
  • UEC food IoU: IoU ของ "อาหาร vs พื้นหลัง" บนอาหารญี่ปุ่น
  • Non-food reject: สัดส่วนภาพที่ไม่ใช่อาหารที่ระบบปฏิเสธถูกต้อง และ THFOOD recognised: สัดส่วนภาพอาหารไทยที่ระบบยอมรับว่าเป็นอาหาร

12ประวัติรุ่นของโมเดล v2 → v4

รุ่นสิ่งที่เปลี่ยนผล / บทเรียน
v1-v2SegFormer-B2 แบบ multi-task: หัวแบ่งพื้นที่ หัวทำนายสัดส่วนรวม และหัว food gate · ใช้ Depth-Anything-V2 ประมาณปริมาตร · แบ่งผัก 70/30 ระหว่างหมู่ 3 และหมู่ 4 · ไขมันคิดเป็นสัดส่วนตายตัวของเนื้อสัตว์ตัวเลขจากหัวทำนายสัดส่วนไม่ตรงกับสีที่ระบายบนภาพ · ค่าคงที่หลายค่าตั้งด้วยมือโดยไม่มีหลักฐาน · หมู่ 3/4 ผิดนิยาม
v3ออกแบบคลาสใหม่ 11 คลาสให้ตรงกับหมู่อาหาร (เพิ่มเต้าหู้/ถั่ว ขนม ของเหลว) · ตัดหัวทำนายสัดส่วนและ depth ออก · ใช้ loss CE+Dice+BCE · คะแนน 2:1:1 คำนวณจากพื้นที่2:1:1 บน FoodSeg ลดจาก 13.6 เหลือ 8.1 · แต่ยังพบว่าอ่านหมูสับเป็นข้าว
v3bภาพไทยเพิ่มเป็น 5,808 ภาพ ด้วย pseudo-label ที่ผ่าน flip-TTA + dish prior + ignore · ใส่ภาพที่มีคลาสหายากซ้ำบน FoodSeg แทบไม่ต่างจาก v3 เพราะป้ายมาจาก v3 เอง จึงเรียนความผิดเดิม แต่บนอาหารไทยดีขึ้น (11.6) ซึ่งเพิ่งรู้หลังมีชุดทดสอบไทย
v4 (ใช้งาน)เพิ่มป้ายไทยที่ตรวจด้วยมือ 345 ภาพ (ใส่ซ้ำ ×4) จากกระบวนการ SAM ในหัวข้อ 7ดีที่สุดทั้งบนอาหารไทย (10.7) และ FoodSeg (8.07)
บทเรียนสำคัญ: (1) ต้องมีชุดทดสอบที่ตรงกับผู้ใช้จริง ถ้าวัดแค่ FoodSeg103 เราจะคิดว่า v3b แย่กว่า v3 ทั้งที่บนอาหารไทยดีกว่าชัดเจน (2) การเพิ่มข้อมูลที่ป้ายมาจากโมเดลเดิมช่วยได้จำกัด ข้อมูลที่ตรวจโดยคนแม้มีไม่มากก็ให้ผลชัดกว่า (3) quantization int8 ทำให้แย่ลงราว 1.5-2 จุดบนอาหารไทย บนเซิร์ฟเวอร์จึงใช้ fp32

  • ไฟล์โมเดลเก็บใน Cache API หลังโหลดครั้งแรก และใช้แบบออฟไลน์ได้

14ส่วนเสริม: การอ่านเมนูด้วย Vision-Language Model

มีโค้ดใน backend/vlm.py สำหรับส่งภาพให้ Claude (claude-opus-5-5) อ่านชื่อเมนู วิธีปรุง ส่วนประกอบ และปริมาณในหน่วยธงโภชนาการ (ทัพพี ช้อนกินข้าว ส่วน) รวมถึงประเมินน้ำมันและน้ำตาลเป็นช้อนชา ผลบังคับรูปแบบด้วย JSON schema (structured output) และใช้สัดส่วนอาหารคลุกที่ VLM ประเมินแทนค่ามาตรฐาน 65/25/10 ได้

สถานะ: ปิดไว้ในเวอร์ชันปัจจุบัน และยังไม่ได้ทดสอบกับ API จริง จะทำงานเมื่อตั้ง ANTHROPIC_API_KEY เท่านั้น ถ้าเปิดใช้จะมีค่าใช้จ่ายต่อรูปและภาพจะถูกส่งไปยังผู้ให้บริการภายนอก ซึ่งต้องแก้นโยบายความเป็นส่วนตัวให้ตรงกัน การประเมินปริมาณจากภาพเดียวในงานวิจัยปัจจุบันยังคลาดเคลื่อนได้ราว 30-40%

15ข้อจำกัดและงานต่อไป

ข้อจำกัดที่ทราบ

  • พื้นที่ไม่ใช่ปริมาณ: อาหารที่กองสูง ซ้อนกัน หรือจมในน้ำแกง จะถูกนับตามพื้นที่ที่มองเห็นเท่านั้น
  • หมู่ 5 ไขมันวัดไม่ได้ จากภาพ
  • คลาสที่ยังอ่อน: เต้าหู้/ถั่ว (IoU 1.1 บนอาหารไทย) · ของเหลว (3.4) · อาหารคลุก (18.8) · ขนม (19.7) · ข้าวในโจ๊กและข้าวต้ม
  • ชุดทดสอบไทยมีขนาดเล็ก (3 ภาพต่อเมนู) และป้ายตรวจโดยผู้ตรวจคนเดียว
  • ภาพจาก THFOOD-50 เป็นภาพจากอินเทอร์เน็ต ซึ่งต่างจากภาพที่จะได้จากกล้องห้อยคอทั้งมุมกล้อง แสง และความละเอียด
  • ภาพทดสอบ non-food เป็นภาพ 64×64 ซึ่งง่ายกว่าภาพจริง

งานต่อไปที่แนะนำ (เรียงตามผลที่คาดว่าจะได้)

  1. เก็บภาพจากอุปกรณ์จริง 200-500 ภาพ แล้ว label ด้วยกระบวนการในหัวข้อ 7 ทั้งเป็นชุดทดสอบใหม่และชุดเทรน เป็นสิ่งที่จะบอกความแม่นจริงของผลิตภัณฑ์
  2. เพิ่มป้ายตรวจด้วยมือสำหรับเมนูที่อ่อน: โจ๊ก ข้าวต้ม อาหารทะเลผัด เกี๊ยว แกงกะทิ เต้าหู้
  3. ชุดข้อมูล MyFoodRepo-273 (24,119 ภาพ ป้ายโดยมนุษย์ CC-BY-4.0) ต้องลงทะเบียนกับ AIcrowd ก่อนดาวน์โหลด
  4. ลองโมเดลใหญ่ขึ้น (SegFormer-B4/B5) สำหรับเซิร์ฟเวอร์ ซึ่งไม่มีข้อจำกัดขนาดไฟล์
  5. ปรับ quantization ของเวอร์ชันเบราว์เซอร์ (static quantization พร้อม calibration หรือ fp16) เพื่อลดช่องว่าง 1.5 จุดจาก fp32
  6. ให้นักโภชนาการสุ่มตรวจป้ายชุดทดสอบ
